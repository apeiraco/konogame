Service ownership, fixed-root/generation-child injection, dependency scopes and staged implementation publication remain effective. The source evidence and remaining gaps are in the [comparison report](../007-EXTENSION-SYSTEM-COMPARISON.md).

Subsequent decision: [ADR 0009](0009-APPLICATION-COMPOSITION.md) replaced the historical assembly names, and that composition package was later retired. ## Decision

Validate complete Contribution and Extension/Module manifests before relationships or execution: Feature, Adapter, software, dependencies, supported activation events and Location definitions all have strict boundaries. Reject unknown fields and malformed values without mutating the accepted catalog or invoking loaders. Safely diagnose bad discovery results and malformed items independently. A valid core Module declaration that cannot be registered remains a preparation failure; a malformed item cannot impersonate a core Module to bypass isolation. In-process Standard Schema dataSchema remains an explicit executable hook boundary; ordinary declaration getter rejection does not imply passive schema evaluation or isolation. Installed JSON metadata has no such hooks.

ExtensionRegistry commits catalog changes internally before public notification. A private Symbol-based synchronization path updates AdapterRegistry indexes and both immutable snapshots first. Public `state$`/`results$` are observation channels, not synchronization hooks. `catalogVersion` identifies the committed catalog on snapshots/results; observer re-entry must see consistent descriptors, generations and version. Catalog changes re-evaluate remembered activation events and a bounded cache of distinct complete binding requests, including late Module/Location declarations. The default cache holds 256 requests; cache equality never defines Location/resource identity.

Discovery sources have stable IDs and receive `{ signal }`. `DiscoveryBatch` declares `complete`, contributions, optional diagnostics and restart-required IDs; contributions may declare a revision and `restart-after-load` policy. Lifecycle `refresh(sourceId?)` computes source-owned add/unchanged/replace/remove deltas. Unchanged manifest/revision preserves generation. Incomplete/error/restart-required scans cannot delete unseen old entries; valid additions/updates may still apply. Conflicts do not establish implicit source precedence. Active/activating changes preserve the old contribution and report restart requirements.

`prepare()`/`prepared` only discover and register the catalog. `initialize()`/`ready` additionally run startup activation. Binding can demand an implementation after preparation without implicitly firing startup. Share lifecycle/activation completion Promises before any synchronous observer may re-enter. Keep existing per-generation activation sharing and AsyncLocalStorage wait-cycle detection.

`InfrastructureSettings` configures ordinary budget/scheduler options: discovery/load 15 seconds each, activation 30 seconds, total shutdown 5 seconds and individual cleanup 1 second by default. Discovery/load and activation receive cancellation signals. Deadline or shutdown seals contexts, blocks late registration and observes late promise rejection. Reverse cleanup continues after individual failures; structured diagnostics include phase, source/contribution/generation where available, reason/cause and elapsed time. Overall shutdown timeout reports unfinished/not-started cleanup, and disposal rejects rather than claiming complete release. These are bounded asynchronous waits, not synchronous preemption, process isolation or a sandbox.

Add core-versioned `@konogame/extension-discovery-node` as a replaceable Node implementation; core does not import it. Scan only explicit unique absolute roots, one directory level, with no implicit home/node_modules discovery. `LocalHostOptions.extensionRoots` and the frontend `KONOGAME_EXTENSION_ROOTS` JSON array configure roots. Read data-only `konogame-extension.json` with strict `extension.package.1` envelope: manifest and module `{ entry, factory, options? }`. Options use the public serializable subset. Limit manifest bytes to 1 MiB and package candidates to 256; sort deterministically and diagnose individual failures.

Canonical path/realpath anchoring and relative-entry validation constrain package paths. Revisions include manifest bytes, streamed entry hash and anchored paths; the lazy loader rechecks observations before ESM import and factory invocation. They detect changes without claiming authenticated signatures, a complete dependency digest or atomic protection against arbitrary filesystem races. Attempted Node ESM code is process-cached; changed loaded/attempted packages require a real service/process restart, including failed imports, without query-string hot-reload tricks.

Expose extension catalog `list()`, `.status(id?)` and `.refresh(sourceId?)`, plus catalog-only CLI `extension list`, `extension status [id]`, `extension refresh`. Catalog mode does not trigger startup or execute installed package code. CLI is short-lived and does not persist refresh decisions; long-lived lifecycle callers apply actual deltas. Normal business service creation still initializes startup. Process options add `catalogOnly` and `coreOptions`; a catalog-only process's `ready` is its preparation completion, not startup completion.

## Consequences and scope

The system now has an explicit installed-package source and operational diagnostics while keeping registry, source I/O, activation and binding distinct. Existing Schema 4, Location unknown retention, metadata recovery and game-data boundaries remain unchanged. Synthetic tests exercise invalid declarations, catalog re-entry, late replay, cancellation/deadlines, incomplete cleanup, package revisions, scan faults and lazy imports.

Persistent global/Workspace enablement, generic third-party contribution points, marketplace/download/install UI, watchers, independent host/RPC/remote execution, force termination and hot unload are future work. Implement them when concrete selection, distribution, isolation or long-lived-session requirements establish their policy and protocol. In-process deadlines must never be presented as killing uncooperative code. See [current lifecycle usage](../006-SERVICES-AND-EXTENSION-LIFECYCLE.md) and the [comparison report](../007-EXTENSION-SYSTEM-COMPARISON.md) for exact APIs, evidence and triggers for further work.
