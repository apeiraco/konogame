# 游戏发现与候选录入

状态：提案，2026-10-17。当前尚未实现 Game Module 或发现流程；已有 `save.discover` 也只是契约边界。下述 Feature 名称是候选，不代表 CLI 命令。

本文基于[当前架构](../001-ARCHITECTURE.md)、[Workspace 提案](002-WORKSPACE-CONFIGURATION.md)和[迭代计划](001-INITIAL-ITERATIONS.md)。

## 从历史设计继承的意图

保留[旧发现设计](../archive/005-DISCOVERY-ENGINE.md)中的主动触发、有范围的本地发现、可选联网补全、引擎规则和可选 AI 辅助。[原始讨论](../archive/100-INIT-DISCUSSION-BACKUP.md)第 15 回合描述了期望提供给用户的选择。

把固定四层、按编程语言划分的漏斗调整为可独立选择的阶段。文件名或引擎指纹提供证据，不足以证明游戏身份。AI 响应提供候选，不等于已验证的位置，也不等于修改 Workspace 的授权。

## 用户意图与领域边界

| 候选 Feature | 建议归属 | 结果 |
| --- | --- | --- |
| `game.discover` | Game Module | 显式选择的来源或位置内的候选安装实例。 |
| `game.identify` | Game Module | 候选身份与外部 ID 的匹配建议。 |
| `game.enrich` | Game Module | 带来源的标题、封面等元数据建议。 |
| `save.discover` | Save Module | 已知游戏/安装实例的候选存档或设置位置。 |

Game Module 负责发现流程与游戏身份语义，Save Module 理解存档位置和导出语义，Workspace 服务校验并持久化录入记录。录入初期可以是应用命令，无需为每个内部步骤增加公开 Feature。

用户可以独立导入已知商店库、识别选定目录或补全已有 Game，不要求每次请求运行全部阶段。游戏设置发现是否继续归属 Save，与 Workspace 提案中的待决问题保持一致。

## 范围与执行流程

建议流程为选择范围、收集候选、按需识别/补全、查看证据与冲突，再录入选定改动。预演只产生候选和配置差异建议。

已采纳 Schema 中 Host `roots` 仅作为任意绝对路径别名，供 `fs.relative` 安装位置使用；`fs.absolute` 为默认方式，并继续支持 `managed` 引用。来源不再包含 `roots`。商店库、扫描根、深度和排除项需要独立选择的发现范围；声明来源或 Host 根不等于授权扫描。录入分配小写 UUIDv7 ID 和原文 `uniformName`，文件名后缀不确定身份。参见 [ADR 0002](../adr/0002-WORKSPACE-TOML-AND-TOOLING.md)。

首次启动不自动开始发现。入口优先提供已配置商店库和选定文件夹；全盘请求属于显式扩大的范围。明确遍历深度、排除项、符号链接/reparse point 处理和访问错误报告。本地模式不访问元数据服务或远程模型；联网补全、本地/远程 AI 各自有可见选项。

枚举已配置的 Workspace 成员与搜索未知位置是不同操作。发现游戏库不能执行候选游戏程序；读取详细文件或注册表位置应限定在所选任务及规则的范围内。

流式呈现候选更新，允许查看部分结果和取消。会话内使用稳定候选 ID、有上限的并发和按来源报告的失败。取消后已展示候选仍可供查看，但不会自动录入。可靠的初始会话模型完成后，再考虑持久检查点与进程重启后的续接。

## 候选与证据模型

候选应包含建议的实体类型、已知安装位置、可能的外部标识、建议字段、支撑证据和冲突。每项观察记录来源 Adapter、规则/清单版本、相关路径或来源引用以及观察时间。确定程度采用可解释的匹配类别，不把任意分数表现为经过校准的概率。

区分观察与用户确认的事实。用户修正优先，除非用户明确接受替换。安装身份与 Game 身份分开：两个目录可能是同一游戏的两个安装实例，相似名称也可能对应不同游戏或发行版。重复录入不应产生重复的已登记安装实例。

存档发现需要有类型的 Locator，例如文件系统路径/模式或注册表键，不能强迫所有位置都成为文件路径字符串。平台与变量展开上下文必须明确。导出 Adapter 解释 Locator 并产生流式 Artifact；存储 Adapter 不需要理解注册表语义。找到预期路径与确认其中已有存档数据也是不同的观察。

## 多 Adapter 与 Binding Plan

[当前绑定 ADR](../adr/0001-CAPABILITY-BINDING.md)规定每次请求选择一个兼容 Adapter，原型继续明确保持这一行为。未来发现流程可以发出多次绑定请求，在 Module/应用层合并观察；不能依赖注册顺序选中一个来源并悄悄丢弃其他来源。

流程根据平台、支持的商店/引擎、请求范围、联网策略和已配置 Adapter 选择来源角色。Capability 描述支持能力，策略决定是否允许参与。显式不兼容的偏好仍需报告失败。Binding Plan 标明已选择的实现和不可用的来源角色；如需新的组合计划 Schema，应另行做契约决策。

建议合并策略为保留来源依据，优先用户明确决策和已验证标识，再考虑文件名启发式；按字段应用来源偏好，遇到矛盾证据时报告冲突而非静默覆盖。相同证据与策略下，结果不应受 Adapter 完成顺序影响。可选来源失败时报告部分结果，不抹去其他成功来源的观察。

## Adapter 与规则策略

先支持显式配置的商店库和本地目录规则。引擎指纹与存档规则独立于 core 版本化，配套代表性目录布局的夹具。缓存所用规则版本，使诊断能够解释当时使用的数据。支持云存档、游戏已安装、本地存档已成功定位是三个不同的观察。

优先通过 Ludusavi Extension 复用已有存档知识。[Ludusavi Manifest](https://github.com/mtkennerly/ludusavi-manifest)描述文件、注册表、平台/商店条件和标识；主数据由 PCGamingWiki 及 Steam 信息生成，并面向其他备份工具开放实现。可把调用 Ludusavi 与读取其清单作为不同 Adapter 实现方案评估，两种方案都不应让上游格式进入 core。来源于 2026-10-17 核对。

联网元数据来源通过各自 Adapter 接入，包含缓存、限流处理与来源特有匹配。存在文档化接口时优先使用。单个商店 SDK DLL、目录名或第三方标题匹配不能独自确定最终身份。

## AI 辅助发现

AI 是用于模糊名称、说明文档解析或存档位置建议的可选 Adapter。运行方式可以是 TypeScript、Python 工具或本地/远程模型端点，领域契约不要求捆绑模型或指定编程语言。

扫描文本作为来源数据处理，不能当作可执行指令。输出需符合 Schema，附有支撑片段或引用；证据不足时明确返回未知。根据允许的上下文校验建议路径，能检查存在性时执行检查；游戏尚未创建存档时保留不确定性。本地模式不能通过 AI 回退上传内容。

规则产生的改动与 AI 产生的改动经过同一个录入服务。不使用 AI 时，也应有可检查的结果和人工修正。未来如需自动录入策略，必须明确范围与冲突行为；首版不包含自动录入。

## 录入与用户体验

审核界面展示候选分组、来源证据、未解决的匹配以及将产生的 Workspace 改动。用户可以接受、编辑、忽略或排除候选，并单独选择补全。忽略候选不能删除已有 Game。

录入按照[配置提案](002-WORKSPACE-CONFIGURATION.md)检查目标 Workspace 修订。发现期间配置发生变化时，应重新计算差异并在写入前报告冲突。保存已确认关联及必要来源信息；详细扫描观察的独立保留策略仍待决策。录入不触发启动游戏、应用补丁、移动存档或备份。

[前端提案](004-FRONTEND-EXPERIENCE.md)定义渐进结果与任务呈现。CLI 和 UI 应通过共享应用服务使用相同的候选 ID、审核决策和错误。

## 首次交付与待决问题

先交付一个有范围的本地发现来源，并在契约夹具中加入第二个模拟 Adapter，验证合并行为。在联网补全之前，完成显式审核和感知修订变化的录入；随后接入基于 Ludusavi 的存档定位，再增加可选元数据与 AI Adapter。

在已采纳 UUIDv7、原文统一名和安装位置规则基础上，需要明确跨来源身份匹配、存档 Locator 表达、来源存储、取消边界、来源排序，以及多次绑定是否需要公开的聚合契约。契约夹具测试语义结果，而非厂商特有输出形状。广泛后台索引与全盘自动化留待后续策略决策。

## 验收目标

- 首次启动不执行未请求的发现；本地会话不发起网络请求。
- 有范围的扫描可以取消，并能报告无权访问的目录，不修改 Workspace 记录。
- 两个 Adapter 报告同一安装时合并证据；模糊身份与不同安装实例仍可区分。
- Adapter 完成顺序变化不影响结果，部分来源失败仍可见。
- 文件系统与注册表存档位置都可以表达，无需存储层理解二者。
- 审核保护已有用户修正，重复录入不产生重复记录。
- Workspace 修订变化阻止过期录入；AI 输出不能跳过校验与审核。
