# Konogame agent guide

## Communication and language

- Chat with the user in user language. For example, if user uses Chinese, chat in Chinese. If user uses English, chat in English.
- Write code identifiers and comments in English. Comments explain why.
- Maintain English and Chinese versions for user-facing architecture, ADR, roadmap, and README changes. Keep machine-oriented files in English.

## Naming

- Do not introduce the token `runtime` in identifiers, comments, documents, messages, or APIs. Its meanings are easy to confuse and misuse. Name the actual role, such as publication, process, host, or generation. The only exceptions are an established community term copied from an external project, including Effect's `Runtime` and an explicit reference to the Node.js language runtime. Do not create another one.

## Source of truth

- Read `README.md` and `docs/en/001-ARCHITECTURE.md` before changing architecture.
- Current decisions are in `docs/{lang}/adr/`; future work is in `docs/{lang}/roadmap/`.
- `konogame-metadata.toml` is the canonical source for project metadata, the shared core release version, Contract protocol/range declarations, and independently versioned Extensions. Maintain package manifests and generated release metadata with `just dev-cli release sync`. Agents may call the forwarded `pnpm dev-cli release sync`. Never edit generated version/metadata files directly.
- Core binaries/packages share one release version. Each Extension has an independent version and declares its Contract range and corresponding software versions in its own `software` map. Software may use SemVer ranges, `latest` for unpinned/insufficiently tested support, or `generic` for protocol/format compatibility. Contract ranges must be valid SemVer ranges. Do not introduce a separate integration registry or provider concept.
- Maintain root `CHANGELOG.md` and `docs/zh/CHANGELOG.md` together; `docs/en/CHANGELOG.md` is a relative symlink to the root source. Core release sections use the version; Extension sections use `<extension-id>@<version>`. Version maintenance does not manufacture release notes.
- `docs/{lang}/archive/` contains historical proposals and discussion records. Do not treat their Rust server, plugin tiers, IPC, or database choices as current contracts.
- Preserve unrelated local Git changes and untracked files.
- During the local experimental phase, allow breaking schema/API changes. Do not add historical migration or backward-compatibility scaffolding unless explicitly requested; preserve user data and report incompatible records.
- `projections/` contains ignored links to private experimental Workspaces. Read their applicable instructions before writing. Keep real paths, account identifiers, and observed game inventories out of public fixtures; use synthetic test data.

## Multi-language documentation

- Use `docs/en/` and `docs/zh/` for English and Chinese. Keep filenames identical across languages, without language suffixes.
- Keep current topic documents flat as `docs/{lang}/00x-TITLE.md`, accepted ADRs under `docs/{lang}/adr/000x-TITLE.md`, and future proposals and plans under `docs/{lang}/roadmap/00x-TITLE.md`.
- Move superseded designs and historical discussion records into `docs/{lang}/archive/`. Keep their original content, updating notices and links as needed. Release history belongs in `CHANGELOG.md` when present.
- English convention documents (`README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `SECURITY.md`, and `PRIVACY.md`, when present) have suffixless repository-root sources. Expose them under `docs/en/` through tracked relative symlinks; keep translations as regular files under `docs/{lang}/`. Do not maintain duplicate homepages or a separate `docs/README.md`.
- Translate user-facing documents, not machine-oriented instructions such as `AGENTS.md`. Archived records may remain in their original language when no translation exists.
- End each current user-facing document with both English and 中文 language links to canonical sources. Link paired archived documents in both directions; do not invent translations for unpaired records.
- Link to documents in the same language whenever available. Resolve links in symlink projections relative to the canonical source.
- `just dev-cli check-docs` recursively checks both language trees, including ADRs, roadmap, and archive, and checks each canonical source once. Agents may call the forwarded `pnpm dev-cli check-docs`.

## Boundaries

- TypeScript is the initial implementation language. Use pnpm workspaces and mise for tooling. `just` is the user-facing command entry.
- Prefer modern native APIs supported by the Node, such as `Temporal`, `Intl`, `import.meta`, and `node:util`'s `styleText`. Use legacy APIs such as `Date` only in small, isolated conversions required at external-library boundaries. Do not add or use legacy utility libraries whose functionality is largely covered by modern native APIs; verify Node support before choosing an API.
- Biome owns formatting, recommended lint rules, and import organization. Use two spaces, LF, double quotes, and inline type specifiers (`import { A, type B }`). Reject `enum` and `const enum`; preserve generated release projections. Use `just lint` to check and `just format` for formatting and safe fixes.
- Target Node 26 ESM. A script exports functions for its caller, or it is a process entry whose work runs only under `if (import.meta.main)`. Importing it must not read arguments, register hooks, change the process, or start work. An unguarded top-level script is allowed only when the host cannot load a module. Use `import.meta.dirname` and `import.meta.filename` where needed.
- Build each package with tsdown without bundling into its own `dist` JavaScript and declarations; package exports target built artifacts. Run `just build` before using package entry points. Use Vitest for tests.
- Share TypeScript options in `tsconfig.base.json`. Root and workspace `tsconfig.json` files are references-only solutions for `tsconfig.{app|lib|tool|test}.json`; each package has a dedicated `tsconfig.test.json`. Reference production dependencies explicitly and exclude tests from production projects. Leave `erasableSyntaxOnly` disabled: tsdown and Vitest compile TypeScript, so constructor parameter properties are valid. Declare an unchanged constructor dependency as a parameter property instead of a second field plus an assignment. Keep an ordinary field when the stored value is derived.
- Put the `monorepo-tsc` source condition before `types`/`import` in workspace exports; enable it through TypeScript `customConditions` so editor navigation and type checking use source. Execution exports use `dist`. `just typecheck` forwards to `pnpm typecheck`, which runs `tsc --build`, with declarations, declaration maps, and incremental metadata in ignored `dist-tsc/` directories. A test-only subpath uses the `test` condition, points at source, and sets `default` to null. `tsconfig.test-base.json` places `test` before `monorepo-tsc`; production projects do not enable `test`. Vitest replaces `resolve.conditions` with its server defaults, so `vitest.config.ts` puts `test` back on those server environments. Export one Layer per replaced service, and do not re-export that subpath from the package entry.
- Workflows live in the module that owns the capability, as a `Context.Service` and Layer. `packages/infrastructure` owns registries, activation, lifecycle, binding, Location, ID, time, binding plans and the extension catalog. `packages/workspace` owns Workspace inspection and edits. `packages/game` owns discovery preview and admission and may depend on `workspace`. `packages/save` owns save writes. CLI and daemon each merge those Layers and select filesystem/Steam/installed sources. `extension` commands only prepare the catalog; other CLI commands initialize. Add `packages/layer-composition` only when several cross-feature combinations cannot live in an existing module. No Application aggregate, ApplicationContext, injector, ready or dispose handle.
- Use Optique command parsers and `@clack/prompts` for TTY menus/missing arguments. Respect flags > environment > TTY, disable prompts for JSON/non-TTY execution, and do not write on cancellation. Enable Bash, zsh, fish, PowerShell, and Nushell completion. Reuse existing arktype constraints through Standard Schema.
- Human Workspace configuration is TOML 1.0; machine output, JSON Schema, and Artifact manifests remain JSON. Keep the common JSON-compatible value subset, explicit `settings.clear`, and schema 4 rules; reject null, dates/times, non-finite numbers, and unsafe integers.
- Boundary validation accepts a Standard Schema or a JSON Schema document and evaluates it with arktype. Schemas that leave the process, including Location `dataSchema` and exported Workspace JSON Schema, are transmitted as JSON Schema. Convert JSON Schema to arktype with `@ark/json-schema`, and convert back with arktype `toJsonSchema`.
- Generate lowercase UUIDv7 for new Workspace/entity and Artifact IDs. UUID alone is identity; preserve original `uniformName` and the versioned `unicode-fs-v1` filename codec. Keep flat/directory record layouts equivalent and reject duplicate UUIDs.
- Keep rename on the existing configuration Port with `configuration.rename`; preserve comments, layout, UUID references, and Host companion containers. Keep lock/revision/hash/recovery behavior scoped to rename, additive import, initialization and single-record edit workflows, sharing writer coordination and reporting visible conflicts and recovery-required failures. Host roots are arbitrary absolute-path aliases passed as context to relevant Adapters; core does not interpret filesystem path semantics. Discovery scan scope is separate from source declarations.
- Workspace management uses explicit initialize/recover-initialize/edit/recover-edit Operations and Capabilities on the existing configuration Port. Edits are one-record strict metadata.replace/settings.replace/host.create/host.roots.replace/host.sources.replace intents, never arbitrary patches. Preserve UUIDs, uniformName, references, Location and external identities; uniformName remains on rename.
- Initialize only a caller-selected existing root, exclusively mkdir .konogame, publish a bounded file set without replacement and workspace.toml last; do not claim portable atomic directory publication. Default history is disabled, new Hosts use directory layout, and only .konogame/.gitignore excludes local/cache/recovery. Existing/incomplete directories without valid journals require manual inspection; never overwrite or alter the root .gitignore.
- Edit preview is read-only and records root/workspaceId/raw revision/operationId/intent/differences/read+apply bindings/digest; a read-only Adapter may preview with apply unavailable. Apply independently anchors caller root and rebuilds the fresh review. settings.replace replaces one persistent layer: omission inherits, clear explicitly clears inherited values, [] is an explicit empty array, and empty Host/Game settings remove the override. CLI title-only preserves edition; raw metadata omission or explicit unset removes it.
- Referenced Host sources cannot be deleted or change kind; status may return to planned with references visible in queries. Roots remain opaque Adapter context and grant no scanning permission. Initialization/edit share writer coordination and targeted journals with rename/import; recovery completes approved metadata without Location execution. Preserve unrelated TOML bytes/comments/layout/newlines, report last-check external-editor races, and do not equate unchanged record bytes with zero filesystem coordination writes.
- Model identity deliberately: Game/Host/Installation are UUID entities; scopes, evidence, and candidate observations have value semantics. Candidate keys are not Game identities. Classify new objects explicitly: entities use stable IDs; value objects compare by value. Schemas and domain services enforce current invariants; classes encapsulate complex behavior.
- Domain services express domain rules; application services coordinate Ports, bindings, review, and persistence. Extensions own vendor parsing and location-specific I/O. Core `packages/workspace-configuration` owns TOML, metadata layouts, read/rename/import/initialize/edit and targeted recovery algorithms; its module-owned `core.workspace-configuration` Adapter belongs to `konogame.workspace` and shares the core version. Existing Node read/rename transport remains there; import I/O is typed and injectable.
- Use exactly `effect`, `@effect/platform-node` and `@effect/vitest` 4.0.6 with actual `Context.Service` owner tags and native Layers. Declare every external dependency version once in the default catalog in `pnpm-workspace.yaml`; manifests use `catalog:` and `catalogMode` is `strict`. Keep `workspace:` for workspace packages. Package release versions stay in `konogame-metadata.toml`, not the catalog. Do not wait with a serial `yield*` unless the next step uses the previous result. Collect independent effects with `Effect.all`, map a collection with `Effect.forEach` and an explicit concurrency, and fork with `Effect.forkChild` then `Fiber.join` or `Fiber.joinAll` when the workflow needs the fiber handles. Side-effecting Ports/Adapters/workflows return `Effect<Success, Error, Requirements>` with owner tagged errors; pure schemas/rules/values/parsers stay pure. Promise/run bridging belongs only at real Node/Optique/Clack/dynamic-import/process/framework/test boundaries. Do not add old DI/Promise compatibility, handmade Env/application contexts, provider arrays or a second service registry. Contract protocol is 0.2.0 with >=0.2.0 <0.3.0; release versions and Schema 4 remain unchanged.
- Classify expected rule/schema refusals at their owner with stable tags and structured issues, never by message or operation text. Rule bridges preserve known typed error objects as Fail; unknown trusted pure-code throws remain Die. UnexpectedBoundaryError is only for explicit third-party boundaries, not a whole-workflow catch-all or exhaustive claim about arbitrary hooks. Preserve natural Port unions and native filesystem tag/code/cause; public Workspace configuration failure protocols do not move implementation classes into domain packages. Recover workflow statuses only from all-Fail Causes, never Die/Interrupt.
- Keep services, Ports, Context.Service tags, errors and provide Layers in their owner package. Core owns registries, activation, lifecycle, binding, Temporal/ID services and generic LocationBehaviorService/LOCATION_BEHAVIOR without business Module/Extension imports. Application owns business services, configuration owns configuration I/O, and Game owns discovery I/O. Composition assembles owner Layers and sources; business packages never import composition. Concurrent implementations use distinct tags. Root Layer overrides win over defaults.
- Gather declarations through one internal multi discovery-source contribution flow. Discover manifests with activationEvents and contributes.adapters/locations before loading implementation code. Pure manifest/provider entries must not statically import implementations. An internal catalog commit synchronizes both registries before public state/results observation; public result Streams does not drive AdapterRegistry synchronization. BindingService lazily activates selected compatible contributions and dependencies before implementation access. Honor explicit events; inferred demand must not activate every candidate. Filesystem/Steam do not declare onStartup.
- Keep core root assembly in one native Layer with typed InfrastructureServices access via Deferred.poll. Early construction access must fail with InfrastructureError at Providers phase rather than wait or expose partial state; publish only the complete graph after lifetime registration. Erase requirements only at validated dynamic Extension execution boundaries.
- ExtensionModule supplies an optional native Layer or activation-context Layer factory and Effect activate. Core builds one Layer/Scope per generation after loading; fixed root overrides win, and dependencyServices accesses only declared active dependency contexts. No child injector or duplicate service registry. Filesystem lazy loaders call createFilesystemExtensionModule with composition-supplied saveRoot; Extensions do not infer home.
- Registries/activation/lifecycle own private PubSub channels and expose read-only Streams/snapshots. Native Deferred/Fiber share asynchronous completion per generation. prepared/prepare only discovers/registers the catalog; initialize/ready additionally performs startup. Business Layer acquisition awaits initialization; catalog-only commands never trigger startup. Stage implementations until success, cache code failures per generation, and retain missing/version/cycle diagnostics for re-evaluation without disabling unrelated contributions. Stream consumers are scope-owned fibers.
- Added implementations need no root-preinstalled Extension services. Remove/replace only inactive contributions without active/activating dependents and without restart-after-load attempted-code restrictions; otherwise return restart-service-required without mutation, including failed loader attempts. No Extension-only reload or automatic restart exists. Native Scope owns application/generation resources through scoped Layers, acquireRelease/acquireUseRelease and finalizers; one owner releases each resource. Business code does not call destructors or add repeated-destruction guards. Preserve external libraries' existing disposal semantics; WeakMap/WeakRef cover caches that must not retain objects.
- Validate complete strict Contribution/Module/Extension/Feature/Adapter/software/dependency/event/Location declarations before relationships or loaders. Reject unknown fields atomically; safely isolate malformed discovery results/items, including sparse arrays. Standard Schema dataSchema is an explicit executable schema boundary (its hooks may run); ordinary plain-declaration getter rejection is not a claim that schema hooks are passive or sandboxed. External installed manifests remain data-only JSON. Internal catalog commits update both registry indexes/snapshots before public notification, with catalogVersion and re-entry consistency. Replay late Module/Location declarations against remembered events and up to 256 distinct complete binding requests by default; request-cache comparison never defines resource identity.
- Discovery sources have stable IDs and cancellable DiscoveryBatch results with complete/revision/diagnostics semantics. refresh computes source-owned add/unchanged/replace/remove deltas; incomplete/error scans never delete unseen old entries. Preserve unchanged generations and report active/attempted-code changes as restart-service-required. Do not silently override conflicts across sources.
- packages/extension-discovery-node owns explicit absolute-root, one-level, data-only konogame-extension.json scanning, strict extension.package.1 module entry/factory/options, 1 MiB manifest/256 candidate limits, canonical/realpath anchoring and manifest+streamed-entry hashes. Recheck observations before lazy import; revisions do not hash the whole dependency tree or authenticate code. No default home/node_modules scan; attempted Node ESM updates require a real process/service restart, not cache-busting URLs.
- Register cooperative custom Extension cleanup with core addLifetimeFinalizer (packages/infrastructure/src/services.ts): native Effect.addFinalizer plus interruptible individual/remaining-total LifetimePolicy budgets, without a second executor. Ordinary acquireRelease/addFinalizer and library resource releases retain native Scope semantics and default interruption protection even without explicit Extension masking; 1s/5s is not a universal hard deadline, and interruption never proves handles have closed.
- Native Scope/Fiber/Deferred/Clock provide cancellation/deadline budgets: discovery/load 15s, activation 30s, total shutdown 5s and individual cleanup 1s by default. TestClock controls tests; do not implement a detached cleanup scheduler or patch fiber internals. Seal late publication, continue cooperative reverse cleanup and report structured diagnostics/incomplete cleanup. Synchronous non-yielding or deliberately uninterruptible code cannot be force-stopped or sandboxed in process. Business Ports carry no AbortSignal; true external bridges may use Effect-provided signals. Scoped writer locks release only owned locks, preserve recovery journals on interruption and mask cancellation only for minimal noncancellable native publication. Effect 4.0.6 nested acquireUseRelease under real Fiber.interrupt may omit an additional finalizer failure from the outer Cause; recovery-required finalizers must first log via native Effect Logger, with entry Logger.LogToStderr protecting JSON stdout. Ordinary failures remain typed and cancellation remains Interrupt.
- Use classes for stateful services, complex Adapters, and mutually referring methods, with controlled private/protected access. Do not hide large workflows in `createXxxx` closures or function collections. Small pure helpers and composition factories remain appropriate. Classes with several named factories use a protected constructor and static factories, without constructor overloads.
- Design replaceable I/O, clock, ID generation, configuration Ports, and discovery Adapters from the start. Tests execute injected replacements through real workflows. DI assembles objects; Binding Plans independently validate domain compatibility.
- Game discovery uses explicit scope and an existing configured Host/source. Preview is read only; admission requires selection/confirmation, strict schema, independent root anchoring, and current revision/evidence/binding checks. Digests detect changes, not authenticated signatures. Keep import journal/forward recovery distinct from rename rollback; do not promise general transactions or replay stale previews.
- CLI and daemon are process boundaries. Put a workflow in the module that owns the capability; call module ports, not vendor tools.
- Keep Module, Feature, Port/Contract, Operation, Capability, Extension, Adapter, and Binding Plan distinct. A capability such as history support is not a sub-feature.
- Game, Host, and Installation are entities, not implementation providers. Workspace uses the same Module/Feature/Port/Adapter binding flow; Provider only describes an Adapter's supplying role, never a second registry or protocol. Use `adapterId`, `adapterOptions`, and source `kind` for their distinct purposes.
- Define finite value sets with `const X = { ... } as const; type X = (typeof X)[keyof typeof X]`. Reuse those values in schemas and discriminants; do not use TypeScript enums or standalone literal-union type declarations.
- Workspace stores only the serializable `LocationContract` envelope `{ type, schemaVersion, data }`. Unknown type/schema stays readable, displayable, and preserved as unverified/unavailable; never execute it as a valid resource. Do not restore LocationKind or a core path resolver.
- ExtensionRegistry registers stable Location type definitions, schemaVersion/schemaRange and portable JSON Schema, never configured instances. AdapterRegistry registers descriptors and typed implementations, checking owner, Contract, Operation, Capability and Location type/schema support on every operand. Location compare/resolve uses Ports, never path/JSON equality; resolution may return a non-path typed resource.
- AdapterDescriptor/Binding use `owner: { kind: module | extension, id }`. Core configuration reads do not require a Location Extension. Extensions may declare dependencies with version and cycle validation, and may reuse filesystem services. Do not introduce a fake core Extension. Bundled/injected sources support lazy activation and live catalog management; Explicit Node installed-package discovery is implemented; marketplace/download and independent host isolation are not implemented.
- An Extension may contribute several Adapters. Resolve each requested Feature against contract version, operation, required capabilities and Location schemas before execution. Explicit preferences fail visibly if incompatible. Fresh admission needs valid/comparable locations; pending import recovery restores approved configuration metadata without executing Location resources and must not gain a Location-registration gate.
- Treat Artifact as an opaque cross-module Stream of files and metadata, with per-file byte Streams opened on demand and handles owned by Scope. Never buffer a whole game asset or assume one file.
- Filesystem storage is the default. Discovery, Workspace configuration, installed Extension packages, and saves call `node:fs` through their owner ports. Effect's `FileSystem` is not that seam. Do not require snapshot history, network sync, or a running daemon for basic local work.
- Keep experimental integrations behind ports. Do not add Kopia, Ludusavi, OpenDAL, Trilium, Syncthing, Rclone, or RustFS as core dependencies without a concrete use case. A future virtual or remote store is an Extension that implements the existing owner ports.

## Command entry

- `just` is the user-facing command entry. Every daily command needs a root `justfile` recipe that forwards to the tool owning that scope. Forward positional arguments with `recipe_args`. On Windows, Just invokes PowerShell 7 so argv stays intact; Unix shells pass native positional parameters.
- pnpm owns workspace scripts such as `build`, `typecheck`, `test`, and `check`. Node owns the built CLI, daemon, and dev-cli modules. Future Cargo and uv commands stay in their own scope the same way. Agents may call those tools directly for scoped work.
- `just setup` installs pinned mise tools and workspace dependencies. `just build`, `just typecheck`, `just test`, and `just check` forward to the matching pnpm scripts. `just cli`, `just daemon`, and `just dev-cli` run the built Node entries and require a prior build.
- Recipe comments are the command reference. Use `just --list`. Add a forwarding recipe when a command becomes part of daily use.

## Verification

- Run `just check` after changing the TypeScript skeleton or current docs. It forwards to `pnpm check`, which runs Biome, builds artifacts, checks types, runs Vitest, checks docs, and validates release metadata/notes. Agents may run `pnpm check` directly.
- Classify tests by the workflow they prove. A unit test owns one rule or service, including in-memory composition of its declared dependencies, one Adapter against a real directory, and CLI help, flags, JSON, and refusal to prompt. An integration test is a complete user workflow or an already identified failure of that workflow, such as discovery admission, Workspace rename/import/edit recovery, writer coordination, and cancellation before a write. Integration tests do not start a process. e2e holds one process observation the test process cannot make: import side effects, built argv, a real terminal, a crash, or a resolve hook that would poison later imports. Cover that observation in one process. The built argv smoke and the real terminal do not receive injected services or a faked isTTY. A child process does not choose the category.
- Turborepo owns build prerequisites for build/test/check through pnpm. Preserve local-only build caching and uncached test execution; pass test filters only to Vitest. Direct CLI/daemon/dev-cli recipes still require an explicit build and invoke Node without task logs.
- In-process tests replace an owner I/O port or use a real directory under `temp/tests/`. Do not mount a virtual filesystem. Subprocesses and native filesystem behavior, including permissions, symlinks, rename, and locks, use real directories. A command matrix calls the exported runner in the test process. Start one fresh process only for an observation that process cannot make, and keep that process in an e2e test: import side effects, built argv, a real terminal, a crash, or a resolve hook that would poison later imports. Drive Effect delays with TestClock. Use execa for processes, cli-testing-library for piped output observation, and node-pty for real terminal interaction. Unit, integration, and e2e files share one worker policy. `just test --shard=1/N` slices files for CI after the same cached build.
- Use Vitest: colocate unit tests in `__tests__/*.test.ts`, package or repository integration tests in `tests/integration/*.test.ts`, and package or repository e2e tests in `tests/e2e/*.test.ts`. Filter with `just test --project unit|integration|e2e`; slice with `just test --shard=1/N`. Cover behavior that could regress, especially binding and streams. Use @effect/vitest it.effect with owner Layer replacements and TestClock for controlled effects/time; use it.live for native I/O/live-clock integration. Effect behavior tests return Effects directly without per-test runPromise wrappers and assert typed errors or Exit/Cause. Keep pure schema/parser/value/type tests as ordinary Vitest; bridge Promises only at real external I/O/framework/process/fixture boundaries and keep cleanup scoped or hook-owned.
- Keep disposable test files and subprocess working directories under `temp/tests/` at the repository root or the workspace that owns the test. `temp/` is gitignored and safe to delete. It is for disposable test and local scratch data, not source, committed fixtures, or user game data. Call `createTestDirectory` from `tests/support/temp.ts`. Intermediate entries are a stable lowercase hierarchy; only the final entry is a random lowercase UUIDv7. Do not use `os.tmpdir` or `mkdtemp`: on many Linux systems the operating-system temporary directory is a small tmpfs.
- Do not modify unrelated files or erase user work to make checks pass.
